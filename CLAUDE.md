# HouseholdApp

Household app for any number of people, built with **SwiftUI + Firebase** (Cloud Firestore + Firebase Auth, project ID `jordan-code`). Jordan and his wife use it daily — **never make changes that could wipe or orphan household data.**

Seven tabs, order configurable per device (Settings → Bottom Bar Order): **Chores**, **Shopping**, **Meals**, **Garden**, **Packing**, **Looking For**, **Settings**. The bottom bar shows five at a time and scrolls, by swipe or its arrows; there is no More screen.

## Build & Run

```bash
# Regenerate Xcode project (required after adding/removing Swift files)
xcodegen generate

# IMPORTANT: xcodegen overwrites the entitlements file — restore after every generate
git checkout -- HouseholdApp/HouseholdApp.entitlements

# Build for simulator
xcodebuild -project HouseholdApp.xcodeproj -scheme HouseholdApp -sdk iphonesimulator -destination 'id=4236ECB3-DF1D-4F48-9A8B-EB1A5848D1FF' build

# Install and launch
xcrun simctl install 4236ECB3-DF1D-4F48-9A8B-EB1A5848D1FF <path-to-built-.app>
xcrun simctl launch 4236ECB3-DF1D-4F48-9A8B-EB1A5848D1FF com.householdapp.app

# Build for real devices (free personal team JBZQM9YC55 — per-device destination
# with device registration; generic/platform=iOS may miss devices on the profile)
xcodebuild -project HouseholdApp.xcodeproj -scheme HouseholdApp \
  -destination 'platform=iOS,id=<ECID>' -configuration Debug \
  -allowProvisioningUpdates -allowProvisioningDeviceRegistration build

# Install on a device (must be unlocked)
xcrun devicectl device install app --device <UDID> <path-to-built-.app>

# Deploy Firestore security rules (firestore.rules is the source of truth)
firebase deploy --only firestore:rules
```

`scripts/refresh-sideload.sh` is fired by launchd **every 30 min, every day, 7 AM–11 PM** and refreshes only phones whose last install is **≥3 days old** (`DUE_AFTER_SECS`; free-team profiles last 7 days, so 4+ days without a chance are needed to expire). When nothing is due it logs one line and exits before clearing profiles. Fixed weekdays (Sun/Wed) were tried and dropped: a day with the lid closed was simply lost. Device IDs live in that script; the schedule is version-controlled at `scripts/com.householdapp.refresh-sideload.plist` — edit there, then run `scripts/install-refresh-agent.sh`. Logs: `~/Library/Logs/HouseholdApp/`.

**Refresh-script gotchas** — each of these broke it silently before:
- **Never `launchctl load`/`unload` the agent — use `scripts/install-refresh-agent.sh`** (`bootout` + `bootstrap`). A job registered with legacy `load` can sit in **"needs LWCR update"**: `launchctl print` lists all its calendar triggers, but none ever spawn it (`runs = 0`). That skipped every scheduled refresh Sep 23–Oct 2, 2026, while the Mac was awake. The install script fails loudly if it sees that state; `launchctl kickstart` clears it.
- `devicectl list devices` prints the **ECID** in its Identifier column on current macOS, but printed the CoreDevice UDID on older versions. The availability check must match **either**, or every run reports both phones unreachable and does nothing (this went unnoticed for weeks and let the profiles expire).
- `DUE_AFTER_SECS` must stay well under 7 days; 3 leaves a 4-day buffer for a closed Mac or a phone that's away.
- Stamps live in `~/Library/Application Support/HouseholdApp/` and logs in `~/Library/Logs/HouseholdApp/`, not `/tmp` — macOS purges `/tmp`, which once erased the only evidence of why runs were missed.
- A missed scheduled day is not always a bug: check `pmset -g log` for `Wake` events (field 4 == `Wake`, not `DarkWake`). If the Mac was asleep all day, launchd had nothing to fire on.
- The built `.app` is located by glob, never a hardcoded DerivedData hash.
- The script checks the **embedded profile's expiry before installing**. A build can succeed by reusing a cached binary without re-signing, so "BUILD SUCCEEDED" is not evidence the signature was refreshed.

## Key Conventions

- **xcodegen**: `project.yml` is the source of truth. Never edit `HouseholdApp.xcodeproj` by hand. Restore the entitlements file after every generate. The one exception: when only *deleting* Swift files, removing their lines from the local (gitignored) `project.pbxproj` avoids a regenerate and the signing reset it causes; the next `xcodegen generate` produces the same result.
- **Firestore-first**: All shared data is Codable `*Doc` structs + `*Store` observable classes in `HouseholdApp/Firebase/`. Each store opens a snapshot listener in `HouseholdAppApp.startStores` and exposes `save`/`delete` (guard against empty `householdId`).
- **New subcollections need rules**: add a member-only `match` block in `firestore.rules` AND deploy it (`firebase deploy --only firestore:rules`) — a listener that starts before rules allow it fails with "Missing or insufficient permissions" and does not retry until app restart.
- **Backward-compatible model changes only**: new fields on `*Doc` structs must be optional with a default value so existing Firestore documents still decode and old app builds keep working. No migrations.
- **@AppStorage for device-local settings**: store lists, item-type lists, icon mappings, and notification prefs live in `AppSettings.swift` (JSON-encoded strings). Member names are the exception — they sync via `memberNames` on the household doc. So does "I am": each phone writes `accounts.<uid> = {email, memberIndex}` on the household doc (only its own UID), and the household's copy wins on snapshot because removing a member remaps every account there (`remapAccounts`). `memberIndex` is absent until a phone picks "I am"; `hasChosenMember` tells "not set" from member 0. That map is the only way to show other people's emails — the client can't look up other Auth users.
- **Multi-member support**: household supports N members. Assignment is `assignedToMembers: [Int]` (member indices); empty = Everyone. Because they're indices, **removing a member must remap every stored index** (drop theirs, shift later ones down) or later members inherit the wrong items — `SettingsView.removeMember(at:)` does this for chores (assigned + completedBy), shopping, meals, and wishes (assigned + note authors, removed author → `AppSettings.formerMemberIndex` = 999, not -1, so older builds' modulo color lookup can't crash). Completion logs keep historical indices.
- **Person filter**: `MemberFilterMenu(selection:)` (Utilities/IconView.swift), a trailing toolbar dropdown on Chores, Shopping and Meals — not a segmented bar, which cramped past three members. -2 = All, else a member index; it resets to All if the selected member is removed. Filtering shows items with empty `assignedToMembers` OR containing the selected index. Secondary toolbar actions go in a text-labelled "…" `Menu` (Meals: My Meals, Plan from Spreadsheet), never bare unexplained icons.
- **Row conventions**: 44 pt check-button tap targets, haptic on toggle, VoiceOver summary via `.accessibilityLabel`, `.caption2` (never fixed point sizes).
- **Auto-cleanup**: completed chores, purchased items, past meals, trips ended >1 week ago (cascading to their packing items), and finished plants (fully harvested, or `seasonEndedAt` set via "Done for Season") are deleted once per session on first snapshot (`hasCleanedUp` flag in each store). Saved meals and wishes are long-lived and never auto-cleaned. **Archived meals and trips (`isArchived == true`) are also exempt** — that's the whole point of archiving over deleting.
- **Archiving**: `MealStore`/`TripStore` publish everything in `meals`/`trips` (Settings counts and delete-all rely on that) and expose `activeMeals`/`archivedMeals`, `activeTrips`/`archivedTrips`. Tabs, trip pickers (`MealFormView`, `ChoreFormView`), and the spreadsheet importer's dedupe context must use the **active** lists; use the full list only where archived items should count.
- **Cross-tab links**: `TabRouter` (in `RootView.swift`) owns tab selection, keyed by `AppTab` rawValue so it survives reordering; `router.openMeal(id)` jumps to the Meals tab and opens a meal.
- **Bottom bar is custom, not `TabView`**: `TabView` forces a More screen past five tabs, even with its bar hidden. `RootView` keeps visited tabs mounted in a `ZStack` (opacity 0, no hit testing, hidden from VoiceOver) so they keep their navigation and scroll state, and `ScrollableTabBar` draws the bar. So `.onAppear` in a tab view fires only on first open, not on every switch; use `onChange` of router state for anything that must react later (see `MealListView.handleDeepLink`). The bar hides while the keyboard is up. Its `ForEach` needs `id: \.self`: `scrollPosition(id:)` matches by that identity, and `AppTab.id` is a String, so the default silently never scrolls. Re-tapping the selected tab does nothing (no pop-to-root).
- **Adding a tab**: add an `AppTab` case (never rename existing raw values — they're persisted), a `tabContent` branch, the store in `HouseholdAppApp`, a rules block, and the Settings count + delete-all entry.
- **Prefilled forms**: several flows hand a draft document to an existing form (`ShoppingFormView(item:isPrefilledDraft:)`, `ChoreFormView(chore:isPrefilledDraft:)`, `MealFormView(meal:template:)`). The flag only affects the title — the draft's unused ID means `setData` creates rather than updates.
- **Reminders are rebuilt whole, never per item.** Each store's snapshot calls `NotificationManager.shared.update(…)`; after a 400 ms debounce every pending `hh-` request is replaced with the soonest 60 across all kinds (iOS keeps only the 64 soonest per app and silently drops the rest). Don't add per-item schedule/cancel calls back, and call `setNeedsRebuild()` after any reminder-setting change. A generation counter stops an overtaken rebuild after its `await`.
- **Reminder settings are `notif.<kind>.on/.dayOf/.ahead` + `notifTimeMinutes`** (`NotifCategory`), with defaults registered at launch by `NotifCategory.registerDefaults()`. Chores and shopping inherit the pre-2.2 keys (`notifDueDatesEnabled`, `notifDayOf`, `notifDayBefore`) through those registered defaults — keep reading them there, or an update silently changes what each phone gets.
- **Design system**: `DESIGN.md` (visual tokens + rules, with `.impeccable/design.json` sidecar) and `PRODUCT.md` (users, purpose, constraints) are the design authority, extracted from the code in Oct 2026. Follow them for any UI work: system text styles, semantic colors, member colors via `appSettings.memberColor(at:)`, 12%-tinted backgrounds under full-strength glyphs, no shadows. If a UI change alters the system (new component, new color role), update DESIGN.md and the sidecar in the same PR. The Impeccable skill (`.claude/skills/impeccable/`, `/impeccable <command>`) is installed project-level; its engine binary and hooks are gitignored — restore with `npx impeccable install --providers=claude --scope=project`.
- **Docs are part of every push**: update BOTH `README.md` (features table, project structure, data model) and `CLAUDE.md` (conventions, architecture, new gotchas) in the same PR as the code. Not "when structure changes" — every push. CLAUDE.md loads into context each session, so drift there silently misleads future work; it went stale for ~10 features before being caught.
- **GitHub**: Push changes as PRs on feature branches (repo: jmadamic/HouseholdApp), merge after verifying in the simulator.
- **Commit messages via file**: write the message to a file and use `git commit -F <file>`. Heredoc commits repeatedly break the permission stream in this environment.
- **Signing resets after `xcodegen generate`**: regenerating the project drops the Xcode signing session, so CLI device builds fail with "No Account for Team". Only a **Run from the Xcode GUI** restores it — the CLI cannot. A failed build leaves a stale binary in DerivedData, so **never install after a failed build**; `devicectl` will report success while shipping the old app.

## Architecture

- **Auth** (`AuthController`): anonymous Firebase sign-in on first launch; optional Google Sign-In upgrade links the account and keeps the same UID. Sign Out confirms first, since it drops the phone into a new guest household. There are no sign-in or setup screens: the app goes straight in.
- **Settings shows controller errors**: `householdCtrl.errorMessage` / `auth.errorMessage` surface through one alert in `SettingsView` (they used to be set and never shown). Set them to plain sentences.
- **Household** (`HouseholdController` + `HouseholdDoc`): all data lives under `/households/{id}` with subcollections `chores`, `categories`, `completions`, `shoppingItems`, `meals`, `savedMeals`, `trips`, `packingItems`, `gardenPlants`, `wishes`. **Every one must also be added to `deleteHousehold`'s cascade list** — Firestore doesn't cascade, and anything missed is orphaned unreachable once the household doc is gone. Access = `request.auth.uid ∈ memberIds`, enforced by `firestore.rules`. Join via invite codes at `/invites/{code}` (8 chars; older households keep 6 until Settings → New Invite Code). **Joining must write `joinCodes.<uid>` = the current code**: the rules compare it to `inviteCode`, keyed per uid because a single shared field kept the last joiner's code and let the next account in without one. Members can't change `ownerId`, add accounts, or remove anyone but themselves. A permission error or UID missing from `memberIds` triggers recovery: clear the cached ID, then `autoCreateIfNeeded` **looks up the account's existing household from the server first** (most members, then oldest) and only creates one if there is none — creating unconditionally stranded a phone in an empty household after sign-out/sign-in or a reinstall. **After any rules change, deploy and run `python3 scripts/test-firestore-rules.py`**; never test rules against an existing household (a hand-rolled test once cut the simulator's test household off).
- **Meal ↔ grocery link**: grocery items created from a meal's missing ingredients carry `mealId`/`mealName`; the shopping row shows a badge that routes back to the meal.
- **Notifications** (`NotificationManager`, `NotificationSettingsView`): local-only reminders for chores, shopping need-by dates, garden harvests (each pending one), trips (body counts unpacked items) and meals (counts missing ingredients; off by default). Per kind: on/off, day-of, early reminder 0/1/2/3/7 days; one reminder time for anything untimed; "Remind me about" filters chores, shopping and meals by assignee using "I am". No APNs entitlement — free personal teams can't provision it, so there are no cross-device pushes (that would need Cloud Functions on the paid Blaze plan).
- **Repeat logic**: completing a repeating chore advances its due date (rolling model) and writes a `CompletionLogDoc`; non-repeating chores archive in place. Beyond the presets, `RepeatInterval.customEvery` / `.customWeekday` read a `CustomRepeatRule` on the chore ("every 6 months", "third Tuesday every month"); always advance via `chore.nextDueDate(from:)`, never `RepeatInterval.nextDate` alone.
- **Garden done-for-season**: `GardenPlantDoc.seasonEndedAt` (optional) marks any plant finished, including always-ready ones and ones with pending harvests. `isFullyHarvested` returns true for it, `isReadySoon` false, and cleanup uses `finishedAt` (season end, else last harvest) — never the last harvest alone, or a plant harvested months ago would vanish the day its season is ended. `syncLegacyFields` mirrors it as `isHarvested`/`harvestedAt = seasonEndedAt` for older builds.
- **Deletes + undo**: single-item swipe deletes happen immediately (no alert) and post to `UndoCenter` (in `RootView.swift`, injected from `HouseholdAppApp`); the banner's Undo re-`save`s the captured doc under its original ID. Use a list view's `delete(_:)` helper rather than calling `store.delete` from a swipe action. Deletes that cascade to children (trips → packing items) and bulk deletes (Clear purchased, Delete All) still confirm with an alert. Sheets that delete things add `.undoBanner()` themselves (SavedMealsView), since a sheet covers RootView's banner.
- **Assignees on rows**: use `AssigneeBadges(indices:)` (Utilities/IconView.swift) — initial avatars from `appSettings.memberInitials(at:)`, never a color-only icon or dot.
- **Tappable rows**: use `.rowTap { … }` (RootView.swift), not `.onTapGesture` — it's a real Button (press dimming, VoiceOver button trait) and buttons inside the row keep their own taps.
- **App tint**: green comes from the `AccentColor` asset via `ASSETCATALOG_COMPILER_GLOBAL_ACCENT_COLOR_NAME` in project.yml (the gitignored local .xcodeproj was patched by hand in Oct 2026 to skip an xcodegen run; a regenerate picks it up from project.yml). Don't add `.tint(.accentColor)` at the root — an explicit tint turns destructive swipe actions green instead of red.
- **Lists stay mounted when empty**: overlay `ContentUnavailableView` on the `List` rather than swapping the List out in an if/else. Swapping while a swipe-delete of the last row animates crashes UIKit ("Invalid number of items in section"); GardenView hit this, and Shopping reproduced it on a full-swipe delete of its last item. All swipe-delete lists now follow it (Garden, Shopping, Chores, Meals, Saved/Archived Meals, Archived Trips, Looking For); anything pinned above the list (Shopping's Store/Type picker) stays outside the `List` in the `VStack`. Wrap any always-present `Section` (e.g. one with a footer) in `if !items.isEmpty`, or its footer shows behind the overlay. CategoryListView (grid) and ReadySoonView (no delete) keep the if/else.
- **Garden ↔ shopping**: `GardenPlantDoc` holds a list of `PlantHarvest` (date + amount) or an `isAlwaysReady` flag for herbs. Legacy single-harvest fields are mirrored on every save (`syncLegacyFields`) so older builds still work. Shopping rows show a "Growing" hint via `GardenStore.readySoonPlant(matching:)`, and the item form opens `ReadySoonView`.
- **Looking For** (`WishDoc`): collaborative research — must-have/nice-to-have criteria, dated notes attributed by member index, links. Note editing is gated on the device's "I am" setting: a UI convenience, **not** a security boundary (rules are household-scoped).
- **Spreadsheet import** (`XLSXReader` + `MealPlanImporter` + `MealPlanImportView`): the bundled `Resources/MealPlanTemplate.xlsx` is generated by `scripts/make-meal-template.py` (openpyxl) — **regenerate it and update the importer's header aliases together** when columns change. `XLSXReader` is a deliberate zero-dependency reader (zip central directory + Apple `Compression` raw-deflate + `XMLParser`); it does not support zip64 or encrypted files, which spreadsheet apps never produce at this size. It allocates from sizes declared inside the file, so keep the caps (20 MB file, 64 MB per part). Meals sheet layout is one ingredient per row: a row with blank Date+Meal but an Ingredient is a *continuation* of the meal above; "Need to buy?" is a Yes/No dropdown (`parseYes` also accepts TRUE/✓/x/1); rows whose name starts with "Example" are the template's grey samples and are skipped. The older two-column comma-list layout still imports. The importer never fails a whole file: each row yields documents or an `ImportIssue` with sheet + row, and duplicates against existing meals/items/trips are skipped so re-import is idempotent. Writes happen only from the preview's Import button, in dependency order (trips → meals → shopping → packing).
- **Meal ingredients → shopping**: the cart toggle on an ingredient sets `have = false`; shopping items are created **at save time only** (`createShoppingItems`) and flagged `addedToList`. Never write shopping items mid-edit — cancelling the form would orphan them.
- **Voice entry** (`SpeechCapture` + `VoiceIntentParser`): on-device speech, then a rules parser extracts kind/date/time/assignee and prefills a form for confirmation. Parsing sits behind `VoiceIntentParsing` so a model-backed parser can replace it; Apple Foundation Models were rejected because they need Apple Intelligence hardware (iPhone 15 Pro+) and one household phone is a 12 Pro.
- **Edit pattern**: categories, stores, and item types have dedicated form views (`CategoryFormView`, `StoreFormView`, `ItemTypeFormView`) with name, icon picker, and delete; parents pass `onDelete`/`onSave` callbacks. `CategoryFormView.iconOptions` is the shared SF Symbol list.
